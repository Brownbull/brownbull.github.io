Gastify

An expense tracker for the Chilean market. It reads receipt photos and credit-card statement PDFs, matches each statement line to a receipt, and flags what is missing or needs a look.

Role
Solo. Claude Code as my main coding tool, under a test-first, review-gated workflow.
Timeline
Firebase prototype, November 2025 to May 2026. FastAPI + PostgreSQL rebuild since April 2026.
Built so far
Receipt scan, ledger, statement import with reconciliation, a spending dashboard and shared groups, on a web app and an Android app. 84 API route handlers and 52 database migrations (September 2026).
Status
Runs on a hosted test deployment (sign-in required, disposable data). Not launched; no payments. Rebuild repo is private; the Firebase prototype is live at boletapp-d609f.web.app.

Problem

A Chilean card statement lists one line per purchase: merchant, date, amount. The items are only on the paper receipt. Reconciling the two by hand every month is slow.

Once each receipt is tagged with its card, Gastify does that match itself and shows which lines have no receipt.

Why a rebuild

The first version ran on Firebase, with most of the logic in Cloud Functions triggered by database writes. As features grew, those triggers started firing on each other's writes and colliding, and the order of operations became hard to follow or test. I rebuilt it as a FastAPI and PostgreSQL backend, where each operation is an explicit endpoint or background task that can be tested on its own.

How it works

  • Receipt scanning. The API stores the photo and hands it to a background task. Gemini, called through PydanticAI with a typed output schema, extracts merchant, items and totals; a second typed call assigns item categories. Amounts are normalized per currency in integer minor units (the Chilean peso has no decimals).
  • Statement import. Uploading a statement needs a named card and an explicit consent box for AI processing. Encrypted PDFs ask for the password. For three known Chilean card layouts, a PyMuPDF parser reads the lines from word positions without calling any model.
  • Reconciliation. Each statement line is compared with the user's saved transactions, scanned or typed in. Lines end up matched, statement only or ambiguous; transactions that no line claims end up receipt only. The run reports a coverage ratio and the reasons behind each verdict.
  • Data isolation. Each request sets the user's ownership scope (personal or a shared group) in Postgres, and row-level security on the ledger, statement and reconciliation tables filters by it; scan records are scoped in application code. The API refuses to start if its database role can bypass row-level security, and CI fails if the isolation tests on real Postgres 16 were skipped.

Decisions

  1. Typed LLM output, with arithmetic as the final check

    I did not trust a valid schema to mean a correct receipt. After extraction, a math check compares items + tax − discount with the printed total in integer minor units. A gap of more than one unit marks the scan as needs-review and stores the review signal on the transaction, so the user sees the mismatch instead of a silent save.

    Cost: the check only flags a mismatch; the user still has to open the receipt and fix it.

  2. Plain code first, AI only as a consented fallback

    I made plain code the default path: a statement in one of the three known layouts that parses with confidence 0.80 or more never reaches a model. The upload is rejected unless the consent box is checked, and the consent applies only when the parser cannot handle the file. Below 0.80, Gemini receives compact row evidence (text, row order, coordinates), not the PDF, and returns a typed layout profile that plain code applies to the rows. Each result records which path ran and why.

    Cost: three layouts are parsed by hand-written code; every other statement depends on the fallback.

  3. Reconciliation that explains itself

    I kept matching deterministic. A transaction is a candidate only if it carries the statement's card, has the same currency, a date within 3 days, an amount within 1% and a merchant-name similarity of at least 0.72. Candidates are scored 0.4 merchant + 0.3 amount + 0.2 date + 0.1 card; if the top two are within 0.05 of each other, the line is marked ambiguous rather than guessed. Every verdict stores its reasons, such as exact_amount or date_tolerance:2d.

    Cost: hand-set values (the tolerances are settings, the weights and the 0.05 margin are constants in code), and scanned receipts start tagged as cash, so the user picks the card before they can match.

Limits

  • Not launched. The only deployment holds disposable test data; billing enforcement is off by default and no payment provider is connected.
  • No durable job queue. Scans and statements run as FastAPI background tasks inside the API process, so a restart can drop an in-flight job. Re-uploading the same PDF restarts a statement that had not started extracting; one caught mid-extraction has to be deleted and uploaded again.
  • The Android app is tested on one physical phone with Maestro. iOS is deferred.
