SRE Triage Agent

An incident triage app I built solo, with Claude Code, during the AgentX Hackathon. A reporter submits an incident; the app screens it, asks an LLM for a structured triage using curated notes on the Solidus e-commerce codebase, checks that the files the model cites exist, and records a mock ticket and team notification.

Problem

When someone reports an incident, a person has to read it, judge the severity, find the code involved and notify the right team.

The hackathon asked for an agent that covers that loop for an e-commerce codebase: intake, triage, ticket, notification and resolution. Each team picked its own open-source codebase; I picked Solidus, an open-source Rails store from the organizers' suggested list.

How it works

  • Guardrails before any model call. 24 weighted regex patterns for prompt injection, SQL injection and XSS, with rejection at a score of 0.90. PII is flagged, not blocked; emails, phone numbers, card numbers and Chilean RUTs are redacted from the model's output. A Redis rate limit allows 10 reports per hour per email.
  • Three engines behind one interface. Claude Haiku 4.5 through the Anthropic SDK with forced tool use; Gemini 2.5 Flash through LangChain, with Groq Llama 3.3 as fallback; and an experimental Anthropic Managed Agents session that explores the repo. That engine needs an agent set up outside the repo (its configuration is not published); without one, it returns a keyword-based placeholder. If the chosen engine fails, the next configured one runs; if all fail, the incident returns to "submitted" for a retry.
  • Layered context. Every prompt gets a short architecture map and a component index of Solidus, plus, when the report matches a domain keyword, one deep-dive on that domain (payments, inventory, orders, search, auth or shipping).
  • Traces from a fresh clone. Langfuse runs self-hosted in the same Compose stack. The app creates its account, project and keys at startup and seeds example traces, so a new clone shows one trace per triage. Token counts are recorded for the Claude engine only.

Decisions

  1. One output schema, forced tool use

    All three engines return the same Pydantic TriageResult: P1–P4 severity, category, affected component, summary, root-cause hypothesis, team, confidence, actions and related files. The Claude engine forces the submit_triage tool, so every reply is a tool call; the code still repairs lists that come back as JSON strings, and Pydantic validates the result. The LangChain engine passes the same TriageResult class to with_structured_output, for Gemini and for the Groq fallback.

    Cost: every engine is limited to the fields the schema defines.

  2. Deterministic guardrails before the LLM

    Injection screening uses weighted regexes rather than a model call, so it is free and predictable. PII is flagged but not blocked; when the input contained PII, the model's output is redacted.

    Cost: regexes only catch the patterns they list.

  3. Check the model's file citations

    After triage, every cited path is checked against the cloned Solidus repo. Paths that do not exist are shown as [UNVERIFIED] instead of as fact.

    Cost: it proves a file exists, not that it is the right file.

  4. Claude Haiku 4.5 instead of Sonnet 4

    My first triage commit called Claude Sonnet 4. About 40 minutes later I switched to Claude Haiku 4.5 to cut cost.

    Cost: I chose on cost, not measured quality; there is no labelled test set to compare the two.

Limits

  • No accuracy evaluation. Severity and confidence are the model's own output; there is no labelled test set.
  • Attachments are stored and shown, but the model only receives each file's name, type and size, not its content.
  • Triage runs inside the HTTP request, with no job queue. The experimental engine can hold a request for minutes.
  • Dispatch is mocked: tickets and notifications are database rows. The app has no authentication.
  • In three recorded runs a Claude triage took 12–15 seconds. That is an observation, not a benchmark.
