Archie

Archie is a browser app for learning system design: you wire components on a canvas, run a simulated traffic curve through them, and watch uptime, p99 latency, served requests and monthly cost respond. Scores and suggestions come from deterministic TypeScript engines (a tick-based traffic simulator, a star rubric, a rule-based design grade and a suggestion engine that re-runs the simulation), with no AI model involved. I built it solo, with Claude Code, as a side project between February and July 2026.

How it is built

How it works

  • The catalog is data. The 116 component definitions (count as of 2026-09-22) are YAML files, validated with Zod and loaded into Firestore by an admin script. The browser only reads them (clients have no write access to the catalog), and on later visits it checks one metadata document and reuses the cached catalog while the seed version matches.
  • The simulation is deterministic. A run samples the load curve at 50 points, routes requests through the graph in topological order, splits them evenly at fan-outs and sheds what a block can't serve; latency rises with utilization on an M/M/1-style curve. The whole run is computed at once and then played back, and the 'realistic' traffic jitter comes from a seeded generator, so the same build and settings always give the same run.
  • Quests are scored by rules. The 64 quests ship as YAML inside the app bundle, each with a load curve, targets and a budget. The first star needs the uptime and p99 targets met with the required blocks on the traffic path; only then does the build earn one more star for staying under budget and one for a well-formed graph (no orphaned or unreachable block). The design grade is separate: it averages the blocks' catalog metrics by category and is recomputed on every edit, not by the simulation.
  • 'Try this next' re-simulates instead of guessing. After a scored run, the engine takes the current build and the quest's own load curve, pulls one lever at a time on each block (one replica more or fewer, a cheaper or a bigger variant of the same component), re-runs the simulation for each candidate and shows the best change with its uptime, p99 and cost deltas. If the build already passes, only a saving that keeps it passing counts; if nothing qualifies, it says no single change improves the build. No randomness and no LLM.
  • Guests write nothing. The first quest plays in the browser with no Firebase user; every store that writes to Firestore returns early without a user id, and an end-to-end test enters as a guest, lands in the quest and asserts that no Firestore write went out. In the repo's Firestore rules, signed-in data is owner-only, fields are allow-listed and updates less than a second apart are rejected. The 'AI Prompt' menu only hands you a prompt to paste into an outside LLM; the YAML it returns comes back through the same validated import.
