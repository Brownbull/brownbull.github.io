Side project · September–October 2025 No longer maintained

Policy-document extraction pipeline

An LLM pipeline, run with Claude Code, that turned Chile's eight 2025 presidential programs into 2,469 numbered measures with source references, plus a static site that publishes them with three browser-side quizzes. This page is a post-mortem: where the model's output was wrong, and the checks I would build now.

This page takes no political side and shows no candidate scores or rankings.

Role
With Claude Code, I wrote the standards and the commands (including the self-review loop), ran the normalization, master-table and evaluation passes, and built the site. A university friend ran my extraction command and its self-review for six of the eight programs on his own subscription, on the October snapshot of the PDFs, and sent back the outputs. I also used DeepSeek and ChatGPT along the way.
Timeline
September–October 2025, before the election.
Model
Claude through Claude Code. The project notes say Sonnet 4.5, but the model was not logged per run, and the first extracts (28 September 2025) predate that model's release.
Status
Static site in Spanish, no longer maintained. The main known problems are listed below.

Problem

Chile's eight 2025 presidential programs were PDFs of 36 to 201 pages. They are long, and comparing them by topic is slow.

I wanted to test whether an LLM pipeline could turn them into numbered measures a reader can check against the source, and have fictional voter profiles evaluate each program.

How it works

  • Written standards instead of one-off prompts. Each stage (extract, normalize, evaluate) has a standards document and a Claude Code command that reads it, so every program and profile started from written rules instead of a one-off prompt, though the outputs did not always follow them.
  • One numbering per program. A second command numbers the measures 1..N with no gaps, each with a source reference, so an evaluation can point to "Measure 283" instead of paraphrasing.
  • Markdown as the database. No backend: Eleventy reads the generated Markdown at build time and GitHub Actions deploys to GitHub Pages.
  • Disclaimers and official sources. Profiles are labeled fictional, every page says the site is not voting advice, and each program links to its official PDF. Three places still rank candidates; see Limits.

What went wrong, and what I would do now

The counts in this section come from a re-audit of the repository with Claude Code in September 2026.

  1. 1Self-grading checked format, not facts

    The six extracts that were graded scored 9.5–10; two grade files are empty. Two of the extracts that scored 10 cite text line numbers as page numbers.

    Now: a separate factual check against the source text, instead of the model grading its own output.

  2. 2Text conversion lost the page breaks

    pypdf joined the pages without markers, so in 2 of 8 extracts the model cited text line numbers as page numbers. One 84-page program gave text for only 1 of its pages (35 lines); nothing flagged it, and its extract came from an earlier snapshot.

    Now: keep page markers through conversion, fail the conversion when pages come back without text, and fail the run when a cited page is beyond the page count.

  3. 3The fix for contradictions was another self-check

    In the first round, one profile said a measure existed and another said it did not. I made one master table per program the single reference and re-ran the evaluations against it, with a consistency-check file for 27 of the 28 profiles. Those checks were the model checking its own work again: at least 18 re-run evaluations still cite measure numbers that do not exist in that program's table, and their check files mark them verified.

    Now: start from the shared table, and check every cited measure number against it in code, not with the model.

  4. 4The comparison table dropped scores

    The comparison table came from a Node script I ran by hand, not from the site build. It did not match two hyphenated candidate names to their files, and I last ran it before the final three profiles' evaluations were added, so the comparison page shows 154 of 224 scores. Separately, 4 evaluations have no score the site can read.

    Now: generate the table inside the build from the evaluation files, and fail the build when a cell is empty or a score is unreadable.

Limits

  • The evaluation standard asked each fictional profile whether it would vote for each candidate, so the site ranks candidates in three places despite its disclaimers: a homepage headline asking who the AI would vote for, per-candidate averages on the comparison page, and a top-3 candidate box in the quiz results.
  • The homepage shows a hardcoded count that matches no data (1,547; the data has 2,469).
  • Two candidates' party labels on the site are wrong: they are hardcoded in the site's data file, and one also entered the data in the normalization pass.
  • The 28 profiles were designed, not sampled, so averages across them say nothing about real voters. Model, token use and cost were not logged per run.
