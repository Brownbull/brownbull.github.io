SRE Triage Agent

Una app de triage de incidentes que construí en solitario, con Claude Code, durante el AgentX Hackathon. Quien reporta envía un incidente; la app lo filtra, le pide a un LLM un triage estructurado usando notas curadas sobre la base de código de e-commerce de Solidus, verifica que existan los archivos que cita el modelo y registra un ticket y una notificación al equipo, ambos simulados.

Problema

Cuando alguien reporta un incidente, una persona tiene que leerlo, evaluar la severidad, encontrar el código involucrado y avisar al equipo correcto.

El hackathon pedía un agente que cubriera ese ciclo para una base de código de e-commerce: recepción, triage, ticket, notificación y resolución. Cada equipo eligió su propia base de código open source; yo elegí Solidus, una tienda open source hecha en Rails, de la lista sugerida por los organizadores.

Cómo funciona

  • Guardrails antes de cualquier llamada al modelo. 24 patrones regex ponderados para prompt injection, inyección SQL y XSS, con rechazo a partir de un puntaje de 0,90. Los datos personales (PII) se marcan, no se bloquean; los emails, números de teléfono, números de tarjeta y RUT chilenos se enmascaran en la salida del modelo. Un rate limit en Redis permite 10 reportes por hora por email.
  • Tres motores detrás de una misma interfaz. Claude Haiku 4.5 mediante el SDK de Anthropic con tool use forzado; Gemini 2.5 Flash mediante LangChain, con Groq Llama 3.3 como fallback; y una sesión experimental de Anthropic Managed Agents que explora el repo. Ese motor necesita un agente configurado fuera del repo (su configuración no está publicada); sin él, devuelve un resultado de relleno basado en palabras clave. Si el motor elegido falla, corre el siguiente que esté configurado; si todos fallan, el incidente vuelve al estado "submitted" para un reintento.
  • Contexto por capas. Cada prompt recibe un mapa breve de la arquitectura y un índice de componentes de Solidus y, cuando el reporte coincide con una palabra clave de dominio, una sección en profundidad sobre ese dominio (pagos, inventario, pedidos, búsqueda, autenticación o envíos).
  • Trazas desde un clon recién hecho. Langfuse corre self-hosted en el mismo stack de Compose. La app crea su cuenta, proyecto y claves al arrancar y precarga trazas de ejemplo, así que un clon nuevo muestra una traza por triage. El conteo de tokens solo se registra para el motor de Claude.

Decisiones

  1. Un solo esquema de salida, tool use forzado

    Los tres motores devuelven el mismo TriageResult de Pydantic: severidad P1–P4, categoría, componente afectado, resumen, hipótesis de causa raíz, equipo, confianza, acciones y archivos relacionados. El motor de Claude fuerza la herramienta submit_triage, así que cada respuesta es una llamada a esa herramienta; aun así, el código repara las listas que llegan como strings JSON, y Pydantic valida el resultado. El motor de LangChain le pasa la misma clase TriageResult a with_structured_output, para Gemini y para el fallback de Groq.

    Costo: cada motor queda limitado a los campos que define el esquema.

  2. Guardrails deterministas antes del LLM

    La detección de inyecciones usa regex ponderadas en vez de una llamada a un modelo, así que es gratis y predecible. La PII se marca pero no se bloquea; cuando la entrada contenía PII, la salida del modelo se enmascara.

    Costo: las regex solo detectan los patrones que enumeran.

  3. Verificar los archivos que cita el modelo

    Después del triage, cada ruta citada se verifica contra el repo clonado de Solidus. Las rutas que no existen se muestran como [UNVERIFIED] en vez de presentarse como un hecho.

    Costo: prueba que un archivo existe, no que sea el archivo correcto.

  4. Claude Haiku 4.5 en vez de Sonnet 4

    Mi primer commit de triage llamaba a Claude Sonnet 4. Unos 40 minutos después cambié a Claude Haiku 4.5 para reducir costos.

    Costo: elegí por costo, no por calidad medida; no hay un set de prueba etiquetado para comparar ambos modelos.

Límites

  • No hay evaluación de precisión. La severidad y la confianza son la propia salida del modelo; no hay un set de prueba etiquetado.
  • Los adjuntos se guardan y se muestran, pero el modelo solo recibe el nombre, el tipo y el tamaño de cada archivo, no su contenido.
  • El triage corre dentro de la solicitud HTTP, sin cola de trabajos. El motor experimental puede retener una solicitud durante minutos.
  • El despacho es simulado: los tickets y las notificaciones son filas en la base de datos. La app no tiene autenticación.
  • En tres ejecuciones registradas, un triage con Claude tardó 12–15 segundos. Es una observación, no un benchmark.
